# Project Page Layout

This document defines the standard structure and storytelling approach for project and case-study pages in my portfolio.

The project pages should feel like a visual story rather than a traditional written report.

Use the project content files as the source of truth for the actual project information. Do not invent project details, metrics, responsibilities, or outcomes.

---

## Overall Page Structure

Each project page should generally follow this structure:

1. Project Hero
2. Project Overview / Metadata
3. Context
4. Problem
5. Research / Discovery
6. Insights
7. Opportunity / Direction
8. Exploration
9. Solution
10. Impact / Outcome
11. Reflection / Learnings
12. Next Project

Not every project needs every section.

Only show sections that have meaningful content in the project document.

---

## 1. Project Hero

The hero should immediately communicate:

- Project name
- Short project description
- My role
- Company / client
- Year
- Project type or category
- Hero visual

The hero should be visually prominent but relatively simple.

---

## 2. Project Overview

Present important project information in a compact metadata layout.

Suggested information:

- Role
- Company
- Timeline
- Team
- Platform
- Contribution

Do not display metadata that is unavailable in the project content.

---

## 3. Context

Explain the situation surrounding the project.

This section should answer:

- What was happening?
- Why did this project exist?
- What triggered the project?
- Who was affected?

Keep this section concise and visual where possible.

---

## 4. Problem

Clearly communicate the problem being addressed.

If appropriate, include:

- Problem statement
- User pain points
- Business problem
- Existing experience
- Supporting evidence

Do not turn this into a long block of text if the information can be communicated visually.

---

## 5. Research / Discovery

Show how the problem was investigated.

Possible components:

- Research methods
- User interviews
- Usability testing
- Data
- Existing user flow
- Journey maps
- Competitive analysis

When a process or flow is provided, prefer creating it as an HTML/CSS visual component rather than flattening it into an image.

---

## 6. Insights

Highlight the important findings from the research.

Insights can be presented as:

- Insight cards
- Statistics
- Quotes
- Before/after comparisons
- User journey observations

Prioritize visual hierarchy over large amounts of text.

---

## 7. Opportunity / Direction

Explain how the insights influenced the product direction.

Possible components:

- Opportunity areas
- HMW statements
- Design principles
- Product principles
- Prioritization
- Strategic decisions

---

## 8. Exploration

Show how the solution evolved.

Possible components:

- Early concepts
- Wireframes
- User flows
- Design explorations
- Iterations
- Rejected concepts
- Design decisions

When showing multiple iterations, make the progression easy to understand.

---

## 9. Solution

Present the final solution.

Use:

- UI screens
- Annotated screens
- Interaction examples
- Feature explanations
- Before/after comparisons
- Supporting diagrams

The solution section should focus on explaining the design decisions, not simply displaying screenshots.

---

## 10. Impact / Outcome

Show measurable or documented outcomes when available.

Examples:

- Product metrics
- Adoption
- Conversion
- Engagement
- Business outcomes
- User feedback

Never invent or estimate metrics.

If no measurable impact is available, explain the documented outcome instead.

---

## 11. Reflection / Learnings

Include meaningful reflections from the project when available.

Possible topics:

- What I learned
- What I would change
- Design trade-offs
- Collaboration lessons
- Constraints
- What happened after launch

This section should be concise and personal.

---

## 12. Next Project

End the page with navigation to another relevant project.

Show:

- Project title
- Short description
- Thumbnail / visual
- Link

---

# Visual Components

The portfolio should support reusable visual components such as:

### Flow Diagram

Used for:

- Existing flows
- New flows
- User journeys
- Product processes

### Insight Cards

Used for:

- Research findings
- Key observations
- Tensions
- Design principles

### Statistics

Used for:

- Research data
- Product metrics
- Business information

### Quote

Used for:

- User quotes
- Stakeholder quotes
- Important statements

### Image / UI Gallery

Used for:

- Product screens
- Wireframes
- Visual explorations
- Final designs

### Before / After

Used when comparing an existing experience with the proposed solution.

### Sticky Section Navigation

Long case studies can use a sticky sidebar that highlights the current section while scrolling.

---

# Writing Style

Project pages should:

- Be clear and conversational
- Avoid unnecessary corporate language
- Use short paragraphs
- Prefer visual storytelling over long explanations
- Explain the reasoning behind design decisions
- Be specific rather than generic
- Preserve factual accuracy

Avoid:

- Generic UX terminology without explanation
- Excessive text
- Repeating the same information
- Making unsupported claims
- Inventing metrics or outcomes

---

# Important Rule

This document defines the page structure and presentation principles.

The individual project `.md` files contain the actual project content.

Do not copy the content from one project into another.

If a project does not contain information for a particular section, omit that section rather than inventing content.
